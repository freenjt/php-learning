The 4 Core PHP Execution Lifecycle Stages

Every PHP process transitions through standard engine phases managed by the Server API (SAPI) layer.

1
MINIT (Module Init)

Executed once when PHP SAPI process initializes (e.g. php-fpm master process start).

  • • Extension loading
  • • Global constants registered
  • • Class entries initialized
2
RINIT (Request Init)

Executed before every HTTP request or script invocation.

  • • Superglobals populated
  • • `auto_prepend_file` executed
  • • Output buffering prepped
3
RSHUTDOWN (Request Term)

Fired when script finishes execution, calls exit(), or hits fatal error.

  • • `register_shutdown_function`
  • • Object `__destruct()` order
  • • Memory zval free/cleanup
4
MSHUTDOWN (Module Term)

Executed when web server or PHP process shuts down completely.

  • • Unloads extensions
  • • Frees global resource pools
  • • Closes persistent sockets

Request Shutdown Hooks (`register_shutdown_function`)

Programmatically registering callbacks that execute during RSHUTDOWN regardless of exit status or fatal errors.

Shutdown Handler & Fatal Error Capture 
register_shutdown_function(function () {
    $error = error_get_last();
    if ($error !== null && in_array($error['type'], [E_ERROR, E_PARSE, E_CORE_ERROR])) {
        // Intercept fatal engine crash before output closes
        error_log("Fatal error intercepted in shutdown: " . $error['message']);
        http_response_code(500);
        echo json_encode(["status" => "error", "message" => "Internal System Crash"]);
    }
    // Clean up temporary database locks or metrics
    MetricsCollector::flush();
});

Source: php.net/manual/en/function.register-shutdown-function.php

Critical Rules of `register_shutdown_function`
1. Working Directory Reset

In older SAPI builds or specific webservers, working directory during shutdown may change to root. Always use absolute paths!

2. Multiple Registered Callbacks

Callbacks execute in FIFO (First-In, First-Out) order of registration.

3. Executed After Connection Close

If output buffers are flushed or `fastcgi_finish_request()` was invoked, shutdown output is invisible to the HTTP client.

Ticks & Low-Level Execution Hooks (`declare(ticks=N)`)

Hooking into low-level statement execution for async signal handling, execution profiling, or micro-benchmarking.

Registering Tick Callbacks 
declare(ticks=1);

// Callback triggered every 1 low-level tick statement
register_tick_function(function () {
    // Check for pending POSIX signals (e.g. SIGINT, SIGTERM)
    pcntl_signal_dispatch();
});

unregister_tick_function('tick_handler');

Reference: php.net/manual/en/function.register-tick-function.php

Tick Event Semantics & Overhead

A tick is an event that occurs for every N low-level tickable statements executed by the Zend Engine within the declare block.

• Non-tickable: conditions without body, variable definitions
• Tickable: assignments, function calls, loop iterations
• Performance note: ticks=1 introduces noticeable engine overhead

Object Lifecycle: Instantiation to Destructor (`__construct`, `__destruct`)

Understanding object reference counts, explicit unsetting, and LIFO destruction ordering.

Constructor & Destructor Ordering 
class ResourceHolder {
    private $handle;

    public function __construct(string $resource) {
        $this->handle = fopen($resource, 'w+');
    }

    public function __destruct() {
        if (is_resource($this->handle)) {
            fclose($this->handle);
        }
    }
}

$a = new ResourceHolder('file1.txt');
$b = new ResourceHolder('file2.txt');
unset($a); // Explicit immediate destruction of $a!

Destructors fire when refcount hits 0 or during script termination.

Destruction Sequence Rules
  • Explicit unset(): Decrements refcount. Destructor runs immediately when refcount reaches zero.
  • Script Termination Teardown: Remaining objects are destroyed in LIFO (Last-In, First-Out) creation order during request shutdown.
  • Exceptions in Destructors: Throwing an uncaught exception in __destruct() during request shutdown triggers a fatal engine error.

Object Serialization & Hydration Lifecycle

Managing object state across request boundaries with __serialize / __unserialize (PHP 7.4+).

Modern Serialization Hooks 
class DatabaseUser {
    private string $id;
    private $connection; // Non-serializable resource

    public function __serialize(): array {
        // Exclude connection resource from serial array
        return ['id' => $this->id];
    }

    public function __unserialize(array $data): void {
        $this->id = $data['id'];
        $this->reconnectDatabase();
    }
}

Replaces legacy `__sleep` & `__wakeup` magic methods.

Serialization Lifecycle Execution Flow
1. serialize($obj) called -> Engine checks for __serialize()
2. __serialize() returns array of state properties
3. unserialize($str) called -> Allocates object WITHOUT calling __construct()
4. __unserialize($data) called to restore dependencies/resources

Process Early Detach (`fastcgi_finish_request`)

Flushes response data to client while allowing long-running background tasks to complete in the same request cycle.

`fastcgi_finish_request()` Implementation 
// Output response to HTTP Client immediately
echo json_encode(["status" => "accepted", "job_id" => 9042]);

// Flush all output buffers and close socket connection to HTTP client
if (function_exists('fastcgi_finish_request')) {
    fastcgi_finish_request();
}

// Client receives 200 OK instantly!
// Script continues running heavy background tasks programmatically:
sendWebhookNotifications();
generatePdfReports();

Available under PHP-FPM SAPI context.

SAPI Constraints & Memory Management

Execution Timeout: The script remains bound by max_execution_time ini setting unless extended via set_time_limit(0).

Worker Worker Blocking: The PHP-FPM process remains busy until script termination, delaying subsequent requests assigned to that worker process.

Reference: php.net/manual/en/function.fastcgi-finish-request.php

Nested Output Buffering Stack Lifecycle

Managing output buffer levels (ob_start, ob_get_clean, ob_flush) during execution.

Output Buffer Manipulation 
ob_start(); // Level 1 Buffer
echo "Internal Render Data";

if (conditionFailed()) {
    ob_end_clean(); // Discards output, buffer deleted
} else {
    $content = ob_get_clean(); // Captures string and closes buffer
}

// Check current stack depth
$level = ob_get_level(); // Returns integer buffer depth

Reference: php.net/manual/en/ref.outcontrol.php

Buffer Cleanup on Request Teardown

When a script reaches termination, the Zend Engine automatically flushes all open output buffers in reverse order (LIFO) out to the SAPI layer before firing final connection shutdown.

• `ob_implicit_flush(true)` disables buffering auto-flush
• Output buffers prevent headers_sent() errors!

Memory & Garbage Collection Cycle Collector

How Zend Engine reference counting (zvals) and circular reference garbage collection operate programmatically.

Programmatic GC Controls 
// Enable cycle collector
gc_enable();

$a = new stdClass();
$a->self = $a; // Circular reference created!
unset($a);     // Refcount drops to 1, added to GC root buffer

// Force immediate collection of circular roots
$collectedCycles = gc_collect_cycles();
$gcStats = gc_status(); // Returns memory & root buffer metrics

gc_mem_caches(); // Releases memory cached by memory manager

Source: php.net/manual/en/features.gc.collecting-cycles.php

Root Buffer & Refcount Mechanics

Zend Engine uses a root buffer (holding up to 10,000 possible roots by default).

When the buffer fills or gc_collect_cycles() is called programmatically, the engine performs a synchronous mark-and-sweep algorithm to free unreferenced cycles.

Long-Running Workers vs Standard Request Lifecycles

Managing persistent memory, stat leaks, and state reset in CLI daemons (e.g. Swoole, RoadRunner, queue workers).

Worker Loop State Reset 
while ($running) {
    // 1. Clear static/global state leaks between jobs
    Container::reset();
    clearstatcache(); // Clear file stat cache
    
    // 2. Process payload
    $job = $queue->pop();
    $job->execute();

    // 3. Prevent memory growth via explicit garbage collection
    if (memory_get_usage() > 128 * 1024 * 1024) {
        gc_collect_cycles();
    }
}

CLI processes bypass traditional web RSHUTDOWN automatic cleanup!

Common Long-Running Worker Pitfalls
Static Variable Persistence: Static class properties remain in memory across all loop iterations.
Database Sockets: Idle database sockets may timeout server-side, requiring reconnect checks.

Error Handling & Shutdown Teardown Synergy

Combining set_error_handler, set_exception_handler, and shutdown callbacks for bulletproof recovery.

Global Lifecycle Error Capture 
// Convert PHP Warnings/Notices into ErrorExceptions
set_error_handler(function ($severity, $message, $file, $line) {
    if (!(error_reporting() & $severity)) return;
    throw new ErrorException($message, 0, $severity, $file, $line);
});

// Uncaught Exception Fallback
set_exception_handler(function (Throwable $e) {
    error_log("Unhandled Exception: " . $e->getMessage());
    http_response_code(500);
});

Source: php.net/manual/en/function.set-error-handler.php

Complete Graceful Lifecycle Protection

Combining error handlers with shutdown callbacks ensures that even non-catchable fatal errors (e.g. memory exhaustion, max execution time exceeded) are intercepted before PHP shuts down.
