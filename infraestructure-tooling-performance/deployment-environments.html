PHP Deployment & Environment Taxonomy

Modern PHP deployment structures application releases across six core programmatic pillars.

Atomic Symlink Swapping

Swaps releases atomically using single kernel POSIX syscalls.

  • • mv -T release current
  • • rename(2) kernel guarantee
  • • Zero request drop window
Host & Selector Engine

Programmatic host inventory and multi-server execution targeting.

  • • host('prod')->setLabels(...)

  • • SSH multiplexing & ranges
Shared Persistent State

Isolates immutable release code from persistent environment files.

  • • shared_files (.env)
  • • shared_dirs (storage/)
  • • Unshared file caches
Environment Directives

Programmatic management of runtime INI settings & ENV variables.

  • • getenv() & $_ENV
  • • Production vs Staging INI flags
  • • display_errors=Off
OPcache & Preloading

  • • opcache.preload=preload.php
  • • opcache.validate_timestamps=0
  • • Cache invalidation on deploy
Tasks, Recipes & Hooks

Modular deployment pipelines with failure handlers and rollbacks.

  • • task('deploy', [...])
  • • before() / after() hooks
  • • dep rollback

Environment Management & Programmatic Configuration

Configuring PHP runtimes across environments using environment variables and production INI directives.

Accessing Environment Variables 
<?php
// Reading variables from process environment
$dbHost = getenv('DB_HOST') ?: '127.0.0.1';

// Superglobal $_ENV access
$appEnv = $_ENV['APP_ENV'] ?? 'production';

// Programmatically altering runtime INI settings
if ($appEnv === 'production') {
    ini_set('display_errors', '0');
    ini_set('log_errors', '1');
} else {
    ini_set('display_errors', '1');
    error_reporting(E_ALL);
}
Production Security Guideline:

Never enable display_errors in production. Stack traces expose database credentials and secret paths to end-users.

Development vs. Production Directives

Atomic Symlink Swap Mechanics (`rename(2)`)

How Deployer guarantees zero-downtime releases using POSIX atomic directory entry updates.

Why Naive `ln -sf` Fails

Standard ln -sf target current is NOT atomic! Under the hood, ln -sf executes an unlink(current) followed by a symlink(target, current). During those few microseconds, web requests hit a missing directory and trigger HTTP 404/500 errors.

// The Deployer Atomic Protocol:
1. Create side-channel symlink: ln -s releases/43 release
2. Atomic Kernel Swap: mv -T release current
3. Kernel calls POSIX rename("release", "current")
The Linux kernel guarantees rename(2) is indivisible on a single filesystem. Requests see either the old release or the new release, never an incomplete state!

Deployer Recipe Anatomy (`deploy.php`)

A recipe defines host target configurations, global variables, and custom deployment tasks.

Standard `deploy.php` Recipe 
<?php
namespace Deployer;

require 'recipe/common.php';

// Config
set('application', 'my_app');
set('repository', 'git@github.com:org/app.git');
set('shared_files', ['.env']);
set('shared_dirs', ['storage']);

// Hosts
host('prod.example.com')
    ->setRemoteUser('deployer')
    ->setDeployPath('/var/www/app');

// Custom Task
task('build', function () {
    run('cd {{release_path}} && npm run build');
});

after('deploy:failed', 'deploy:unlock');
Core DSL Primitives
host('alias')

Defines an SSH target machine, IP, remote user, and deploy path.

set('key', 'value' | callback)

Sets global or per-host configuration variables. Callbacks run lazily once per host.

task('name', function () { ... })

Encapsulates bash commands executed remotely over SSH via run().

before() / after()

Hooks custom tasks into existing execution flow pipelines.

Reference: deployer.org/docs/8.x/basics

Shared Persistent State & Writable Directories

Separating static deployment code from stateful files using symlinked shared storage.

Configuring Shared Paths 
// Shared files symlinked into release dir
set('shared_files', [
    '.env',
    'config/secrets.json',
]);

// Shared directories (uploads, logs, storage)
set('shared_dirs', [
    'storage',
    'public/uploads',
]);

// Directories web-server user must write to
set('writable_dirs', [
    'bootstrap/cache',
    'storage',
]);

Shared paths are stored once under /var/www/app/shared/.

The Shared Cache Contamination Trap

Official Warning: Sharing compiled file caches (like route caches or file store paths) across releases causes critical runtime crashes!

Because absolute paths in cached code point to a specific release directory (/releases/42/...), sharing the cache folder leads to broken class imports when users hit new code.

Best Practice: Keep application file cache INSIDE the release folder so each deployment builds its own isolated cache!

Source: deployer.org

Task Flow, Lifecycle Hooks & Atomic Rollbacks

Constructing robust execution pipelines that gracefully handle failures and instant rollbacks.

Custom Lifecycle Hooks 
// Execute DB migrations before symlink swap
before('deploy:symlink', 'database:migrate');

// Reload PHP-FPM OPcache after successful swap
after('deploy:symlink', 'fpm:reload');

// In case of error during deploy
fail('deploy', 'deploy:unlock');

task('fpm:reload', function () {
    run('sudo systemctl reload php8.3-fpm');
});
Instant Rollback Command (`dep rollback`) 
$ dep rollback

# Deployer atomically points `current` 
# back to previous release directory:
# releases/42 -> current
Why Rollbacks are Instant:

Deployer keeps old release folders on disk (keep_releases setting, e.g., 5). Rolling back simply executes a single atomic symlink swap back to the previous release directory!

OPcache Preloading & Production Invalidation

Compiling PHP opcodes directly into persistent shared memory for max execution throughput.

OPcache Preload Script (`preload.php`) 
// In php.ini: opcache.preload=/app/preload.php
// opcache.preload_user=www-data

$files = require __DIR__ . '/vendor/composer/autoload_classmap.php';

foreach ($files as $file) {
    // Compiles files permanently into RAM
    opcache_compile_file($file);
}

Preloading requires PHP-FPM / web server restart to reload preloaded code.

OPcache Cache Invalidation Strategies
1. Reload PHP-FPM Service

systemctl reload php8.3-fpm gracefully reloads worker processes, clearing OPcache without dropping connections.

2. Programmatic `opcache_reset()`

Calling opcache_reset() via HTTP endpoint flushes opcode cache in shared memory.

3. Set `opcache.revalidate_path=1`

Forces OPcache to resolve symlinks (current) for realpath keying during lookups.

Source: php.net/opcache.preloading

CLI vs PHP-FPM Environments & Worker Restart Strategies

Managing persistent background queue workers and scheduled cron tasks across deployment releases.

Queue Worker Graceful Restart 
// In Deployer recipe: Restart long-running CLI workers!
task('workers:restart', function () {
    // Signals supervisor / worker processes to gracefully exit
    // after completing current job so systemd restarts them in NEW release path!
    run('cd {{current_path}} && php artisan queue:restart');
});

after('deploy:symlink', 'workers:restart');

Long-running CLI processes keep old memory in RAM until explicitly restarted!

Systemd Service Configuration 
[Unit]
Description=PHP Queue Worker
After=network.target

[Service]
User=www-data
# Points directly to current symlink!
WorkingDirectory=/var/www/app/current
ExecStart=/usr/bin/php artisan queue:work
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target

Points WorkingDirectory to /current so restarts load latest code.
