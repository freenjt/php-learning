PHP MVC Taxonomy & Separation of Concerns

Separation of Concerns (SoC) isolates application logic into distinct modules, avoiding spaghetti code and mixed HTML/SQL payloads.

Front Controller & Router

Centralized entry point (`index.php`) that parses HTTP requests and routes to handlers.

  • • $_SERVER['REQUEST_URI'] parsing
  • • Single point of bootstrap & config
  • • Uniform response dispatching
The Model Layer (Domain)

Manages data persistence, business logic, validation, and database operations via PDO.

  • • PDO & Prepared Statements
  • • Entities, DTOs & Repositories
  • • Zero HTML or HTTP knowledge
The View Layer (Presentation)

Renders presentation markup using native PHP output control and sanitized variables.

  • • Output Buffering (ob_start)
  • • Templating with extract()
  • • Sanitization with htmlspecialchars()
The Controller Layer

Mediates between HTTP requests, invoking Model methods and selecting View responses.

  • • Consumes $_GET, $_POST
  • • Delegates business ops to Model
  • • Passes clean data to View
Autoloading & Namespaces

Automates class loading according to directory structures without manual requires.

  • • spl_autoload_register()
  • • Declarative namespace scopes
  • • PSR-4 filesystem mapping
Dependency Injection

Passes dependencies explicitly via constructor parameters rather than hardcoding concrete classes.

  • • Type Hinting with interface
  • • Loose coupling & mock testing
  • • Inversion of Control (IoC)

Single Point of Entry: Front Controller & HTTP Parsing

Every HTTP request hits `public/index.php`. Superglobals inspect request methods and URIs before dispatching to Controllers.

`public/index.php` (Front Controller) 
<?php
declare(strict_types=1);

// 1. Register Autoloader
spl_autoload_register(function (string $class) {
    $file = __DIR__ . '/../' . str_replace('\\', '/', $class) . '.php';
    if (file_exists($file)) require $file;
});

// 2. Parse HTTP Request URI using official php.net functions
$requestUri = parse_url($_SERVER['REQUEST_URI'] ?? '/', PHP_URL_PATH);
$requestMethod = $_SERVER['REQUEST_METHOD'] ?? 'GET';

// 3. Simple Router Dispatch
$router = new App\Core\Router();
$router->add('GET', '/users', [App\Controller\UserController::class, 'index']);
$router->dispatch($requestMethod, $requestUri);
php.net Standard:

Superglobals like $_SERVER, $_GET, and $_POST are auto-globals provided by Zend Engine for request metadata.

The Model Layer: Encapsulating Business Domain & Data (PDO)

Models isolate database interactions and domain rules. They know nothing about HTML, HTTP status codes, or superglobals.

Domain Model Repository (PDO) 
<?php
namespace App\Model;

use PDO;

class UserRepository {
    public function __construct(private PDO $db) {}

    /** @return User[] */
    public function findAll(): array {
        $stmt = $this->db->query('SELECT id, name, email FROM users');
        // Fetch strictly as typed objects or associative arrays
        return $stmt->fetchAll(PDO::FETCH_ASSOC);
    }

    public function findById(int $id): ?array {
        $stmt = $this->db->prepare('SELECT * FROM users WHERE id = :id');
        $stmt->execute(['id' => $id]);
        $user = $stmt->fetch(PDO::FETCH_ASSOC);
        return $user ?: null;
    }
}

Source: php.net/book.pdo

Model Layer Core Responsibilities
1. Pure Persistence Independence

Models use PDO prepared statements to execute queries without leaking database connection concerns into views or controllers.

2. Business Logic Enforcement

Rules like "email uniqueness" or "account balance validation" reside exclusively inside domain models or service classes.

3. Portable & Unit Testable

Because Models do not use echo or HTTP headers, they can be unit-tested in isolation using PHPUnit.

The View Layer: Output Buffering & Dynamic Templating

Views consume sanitized data payloads and generate HTML. Output control functions (`ob_start`, `ob_get_clean`) prevent accidental early header sends.

Native View Renderer (`ob_start`) 
<?php
namespace App\View;

class View {
    public static function render(string $template, array $data = []): string {
        // Extract array keys into local variable scope
        extract($data);

        // Turn on output buffering (php.net/ob_start)
        ob_start();

        $templatePath = __DIR__ . "/../../views/{$template}.php";
        if (file_exists($templatePath)) {
            require $templatePath;
        }

        // Capture buffer contents and clean buffer
        return ob_get_clean();
    }
}

Source: php.net/function.ob-get-clean

`views/users/index.php` Template 
<!-- Uses Alternative Syntax for Clean Separation -->
<h1><?= htmlspecialchars($title) ?></h1>

<ul class="user-list">
    <?php foreach ($users as $user): ?>
        <li>
            <strong><?= htmlspecialchars($user['name']) ?></strong> 
            (<?= htmlspecialchars($user['email']) ?>)
        </li>
    <?php endforeach; ?>
</ul>
Security Mandatory Rule:

Views MUST always sanitize raw dynamic output via htmlspecialchars($var, ENT_QUOTES, 'UTF-8') to prevent Cross-Site Scripting (XSS).

The Controller Layer: Orchestrating Requests into Responses

Controllers connect HTTP input with domain operations and output generation, maintaining a slim orchestration footprint.

`UserController.php` 
<?php
namespace App\Controller;

use App\Model\UserRepository;
use App\View\View;

class UserController {
    public function __construct(private UserRepository $userRepo) {}

    public function index(): string {
        // 1. Fetch data from domain Model
        $users = $this->userRepo->findAll();

        // 2. Pass sanitized payload into View
        return View::render('users/index', [
            'title' => 'User Directory',
            'users' => $users
        ]);
    }
}
Controller "Thin Rules"
WHAT CONTROLLERS SHOULD DO:
  • Read HTTP payload parameters ($_GET, $_POST)
  • Invoke Model/Repository operations
  • Return HTTP status codes (http_response_code())
  • Delegate rendering to View engines
WHAT CONTROLLERS MUST NEVER DO:
  • Execute SQL queries directly
  • Echo HTML markup directly
  • Contain core business algorithms

Autoloading & Namespaces (`spl_autoload_register`)

Eliminate repetitive `require_once` calls by registering automated PSR-4 compliant namespace loaders.

Programmatic PSR-4 Autoloader 
<?php
declare(strict_types=1);

spl_autoload_register(function (string $class) {
    // Prefix mapping: App\ => src/
    $prefix = 'App\\';
    $baseDir = __DIR__ . '/src/';

    $len = strlen($prefix);
    if (strncmp($prefix, $class, $len) !== 0) {
        return; // Not in App namespace
    }

    $relativeClass = substr($class, $len);
    $file = $baseDir . str_replace('\\', '/', $relativeClass) . '.php';

    if (file_exists($file)) {
        require $file;
    }
});

Source: php.net/spl_autoload_register

PSR-4 Namespace to Path Mapping
Class Qualified Name:
App\Controller\UserController
↓ Maps directly to filesystem
src/Controller/UserController.php
Class Qualified Name:
App\Model\UserRepository
↓ Maps directly to filesystem
src/Model/UserRepository.php
Separation Benefit:

Strict namespaces isolate class names across independent modules, preventing global function or class collisions.

Dependency Injection & Inversion of Control

Decouple components by injecting interface dependencies via constructors rather than hardcoding concrete instances inside classes.

Interface Constructor Injection 
<?php
namespace App\Model;

// 1. Contract Definition
interface UserRepositoryInterface {
    public function findAll(): array;
}

// 2. Concrete Implementation
class PdoUserRepository implements UserRepositoryInterface {
    public function __construct(private \PDO $pdo) {}
    public function findAll(): array { /* PDO query */ return []; }
}

// 3. Dependent Controller
class UserController {
    // Accepts Interface, NOT concrete class!
    public function __construct(private UserRepositoryInterface $repo) {}
}

Source: php.net/language.oop5.interfaces

Tight Coupling vs. Dependency Injection
BAD: Hardcoded Dependency Inside Class 
class UserController {
    public function __construct() {
        // Tightly coupled! Impossible to mock or change DB
        $this->repo = new PdoUserRepository(new PDO(...));
    }
}
GOOD: Injected Interface Dependency 
// Flexible! Allows passing MockUserRepository in tests
$controller = new UserController(new PdoUserRepository($pdo));

Security & Data Filtering across MVC Layers

Separation of Concerns ensures input validation happens at Controller entry, SQL binding in Model, and XSS escaping in View.

1. Controller Input Filtering 
// Sanitize input at HTTP entry
$email = filter_input(
    INPUT_POST, 
    'email', 
    FILTER_VALIDATE_EMAIL
);

if (!$email) {
    http_response_code(422);
    return View::render('error');
}

Uses filter_input() to reject invalid incoming HTTP data early.

php.net/book.filter

2. Model SQL Parameterization 
// Prevents SQL Injection
$stmt = $db->prepare(
    'SELECT * FROM users 
     WHERE email = :email'
);
$stmt->execute(['email' => $email]);

PDO parameter binding prevents raw string concatenation in SQL queries.

php.net/pdostatement.execute

3. View XSS Escaping 
<!-- Escapes HTML entity characters -->
<span class="user-email">
  <?= htmlspecialchars(
      $email, 
      ENT_QUOTES, 
      'UTF-8'
  ) ?>
</span>

Escapes special HTML characters before writing to client body stream.

Encapsulating HTTP Responses & Status Codes

Strict separation of HTTP header management (`header()`, `http_response_code()`) into dedicated Response objects.

Object-Oriented Response Wrapper 
<?php
namespace App\Http;

class Response {
    public function __construct(
        private string $content = '',
        private int $statusCode = 200,
        private array $headers = []
    ) {}

    public function send(): void {
        // Set HTTP status code (php.net/http_response_code)
        http_response_code($this->statusCode);

        // Send custom headers
        foreach ($this->headers as $name => $value) {
            header("{$name}: {$value}");
        }

        // Output content body
        echo $this->content;
    }
}

Source: php.net/function.http-response-code

Controller Response Dispatching 
// Returning JSON API Response from Controller
public function apiIndex(): Response {
    $data = $this->repo->findAll();
    
    return new Response(
        json_encode($data),
        200,
        ['Content-Type' => 'application/json']
    );
}

// Returning HTML Response from Controller
public function htmlIndex(): Response {
    $html = View::render('users/index', ['title' => 'Users']);
    
    return new Response($html, 200, ['Content-Type' => 'text/html']);
}

Ensures controllers return testable Response objects instead of executing `echo` directly.

Request State & Session Isolation

Abstracting session state (`$_SESSION`) away from views and business models to prevent direct superglobal coupling.

Encapsulated Session Class 
<?php
namespace App\Http;

class Session {
    public function start(): void {
        if (session_status() === PHP_SESSION_NONE) {
            session_start();
        }
    }

    public function set(string $key, mixed $value): void {
        $_SESSION[$key] = $value;
    }

    public function get(string $key, mixed $default = null): mixed {
        return $_SESSION[$key] ?? $default;
    }
}

Source: php.net/function.session-start

State Isolation Architecture Benefits
1. Mocking & Session Testing

Injecting a Session service wrapper allows unit tests to simulate authenticated users without actual session files on disk.

2. Zero View Coupling

Views receive extracted data arguments rather than reading $_SESSION globals directly.

3. Shared Request Lifecycle

Every HTTP request runs independently, preventing state leakage across requests in PHP's shared-nothing execution model.
